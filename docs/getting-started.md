# Getting started

This guide gets the reference application running locally. The examples are not ready to be exposed to the internet.

## Requirements

- Go `1.26.5` or later, as specified in `go.mod`.
- PostgreSQL for the default configuration.
- An empty database that the application can access.

## Set up the application

1. Create a PostgreSQL database and a user for local development.
2. Open `app/config/database.go`. Set the host, port, username, password, database name, and TLS options for your local environment. The checked-in values are examples; do not use the sample password in a deployment.
3. Check `app/config/server.go`. The default host is `127.0.0.1`, the port is `3000`, and CORS allows only `https://app.example.com`. Change the allowed origin to match your local browser client. CORS does not prevent command-line or other non-browser clients from making requests.
4. The configured migration and seeder directories are relative to the process working directory. Run the app from the repository root unless you change those paths.
5. Migrations and seeders run at startup in the default configuration. The schema and sample data files are in `app/database/`. See the [database guide](./database.md).

The application reads configuration from Go source. It does not automatically read a `.env` file or environment variables.

## Run the application

From the repository root, run:

```sh
go run .
```

Or use the Make target:

```sh
make run
```

By default, the server listens at `http://127.0.0.1:3000`. If the database connection fails, check that the database exists and that the connection settings are correct.

Keep the process running while trying the requests below. Stop it with `Ctrl+C` when finished.

## Try an endpoint

List departments:

```sh
curl http://127.0.0.1:3000/examples/departments
```

List users without returning their password field:

```sh
curl http://127.0.0.1:3000/examples/orm-queries/users
```

Create a department:

```sh
curl -X POST http://127.0.0.1:3000/examples/departments \
  -H 'Content-Type: application/json' \
  -d '{
    "id": "dept-local-01",
    "name": "Engineering",
    "description": "Local development department",
    "isActive": true
  }'
```

Create a user with an existing department ID:

```sh
curl -X POST http://127.0.0.1:3000/examples/orm-queries/users \
  -H 'Content-Type: application/json' \
  -d '{
    "id": "user-local-01",
    "email": "user@example.com",
    "password": "local-test-password",
    "departmentId": "dept-01",
    "isActive": true
  }'
```

The PostgreSQL sample data includes departments with IDs `dept-01` through `dept-05`. Use an ID that exists in your selected database. The application uses the GOREST Argon2 helper to hash passwords during user create and update operations that write the password. The user response DTO does not include a `password` property.

For the example relationships, use a `departmentId` and `userId` that exist in your selected database. Create the department and user first, or use IDs from the seed data. Database constraints differ by driver. Resource IDs are supplied by the client in these examples; they are not generated by the application.

For `PATCH`, send only the field(s) supported by that resource. For example, a user patch accepts `isActive` only:

```sh
curl -X PATCH http://127.0.0.1:3000/examples/orm-queries/users/user-local-01 \
  -H 'Content-Type: application/json' \
  -d '{"isActive": false}'
```

For all routes, request body fields, query examples, and driver limitations, see the [API reference](./api-reference.md). To understand how startup and each request pass through the code, see [Architecture and application lifecycle](./architecture.md).

## Development commands

```sh
make test      # Run go test ./...
make check     # Run go vet ./... and then go test ./...
make lint      # Run golangci-lint run ./...
make build     # Build bin/gorest-api-starter
make coverage  # Create coverage.out
make clean     # Remove the binary and coverage.out
```

The `lint` target requires `golangci-lint` to be installed. For more development guidance, see [Adding features](./extending.md).
For default E2E tests, optional MongoDB/ScyllaDB tests, and coverage generation, see [Testing and E2E coverage](./testing.md).
